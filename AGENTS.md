# Agent Instructions

- Permanent UI text rule: use the project's existing localization/string-key workflow for all user-facing UI text. Add or update the appropriate string-table entries and resolve them by key; do not hardcode labels, messages, warnings, or fallback display text in code.

- Permanent user preference: when the user asks to proceed in a new conversation/task, create the new task with Sol (`model: "gpt-5.6-sol"`) and high reasoning (`thinking: "high"`) by default. An explicitly specified model or reasoning effort overrides its respective default. Apply this preference across future conversations in this project.
- Blender modeling host workflow: when a modeling instruction arrives in the Blender script modeling host conversation, create a new task using Astra (`model: "gpt-6-astra"`) with high reasoning (`thinking: "high"`), and have that task perform the modeling work, validate the results, and commit the completed changes. This overrides the general Sol default for those modeling tasks. Answer ordinary questions directly in the host conversation without saving question or request logs for them.
- The Unreal Engine project is `TunaSweeper/TunaSweeper.uproject`.
- When opening Unreal Editor for Computer Use, explicitly open `TunaSweeper/TunaSweeper.uproject` (absolute path: `D:/github/extraction_shooter/TunaSweeper/TunaSweeper.uproject`). Reuse an existing editor for this project when available; do not launch Unreal Editor without specifying the project.
- Treat TunaSweeper as an Unreal Engine 5.7 project.
- Version check: `TunaSweeper.uproject` has `"EngineAssociation": "5.7"`, and both `TunaSweeper.Target.cs` and `TunaSweeperEditor.Target.cs` use `EngineIncludeOrderVersion.Unreal5_7`.
- Prefer UE 5.7-compatible APIs and build settings when editing C++ or project configuration.
- After a build finishes and Unreal Editor can be launched, open the editor for `TunaSweeper/TunaSweeper.uproject` unless the user says not to.
- When the user's entire message is exactly `빌드` or `build` (with no other text), do not add a request-log entry. Build the project, then open the Unreal Editor when it can be launched.

- Only when performing store build packaging or repackaging, read and follow `Docs/store_packaging_checklist.md` before starting. Do not load this checklist for ordinary code edits, editor builds, or unrelated questions.
- Record completed user instructions in `Docs/requests.md` at the end of the task, using `## YYYY-MM-DD HH:mm:ss (소요시간: HH:MM:SS)` as the entry heading. The timestamp is when the user request was received or work began, and elapsed time is measured from that start time until the task is completed or the final response is being prepared. Do not include a timezone suffix, do not use `(elapsed: ...)`, and do not write `00:00:00` as a placeholder.
- Never record work performed in the access-restricted `ProductionPayload` repository in the public `Docs/requests.md`. Record those instructions only in `TunaSweeper/Plugins/QuestDatasetSwitcher/ProductionPayload/Docs/requests.md`. For a task spanning both repositories, record only public-repository work in the public log and only access-restricted-repository work in the access-restricted log; do not duplicate or summarize access-restricted work in the public log.
- Record user questions and their answers separately in `Docs/questions.md` at the end of the response, using the same Korean timestamp and elapsed-time heading format. Do not include a timezone suffix in question log timestamps. Do not duplicate questions in `Docs/requests.md`.
- Treat identifying information for the access-restricted production data repository as sensitive. Never record its remote repository name, URL, account or organization owner, or other remote identifier in public tracked documents, `Docs/requests.md`, or `Docs/questions.md`. Refer to it generically as the access-restricted `ProductionPayload` repository and use only the project-relative local path when operational instructions require a path.
- Do not impose per-change demo-versus-release narrative placement decisions while the demo is still being authored. Until the user explicitly declares the demo narrative frozen and requests isolation, treat current narrative work as demo work. After that isolation milestone, route newly added story text to the release narrative dataset by default; modify the demo narrative only when the user explicitly requests a demo change. Items, meshes, and non-narrative information may remain in the public repository.
- At the post-demo isolation milestone, store each demo/release narrative as a complete dataset-specific pack and switch the narrative pack atomically with the quest dataset and save namespace. The protection boundary is the public source repository and the contents of demo builds: unreleased release narrative must enter neither. The user accepts that purchasers may reverse-engineer the production PAK, so do not add PAK encryption or narrative obfuscation solely to prevent that unless the user later requests it.
- Use `Docs/game_conventions.md` for project-wide gameplay conventions such as direction, distance, units, and currency.
- Before placing or editing `BP_RaidPlacementAnchor`, changing a raid `PlacementId`, or editing `EnemySpawns.json`, `LootContainerSpawns.json`, or `MemoSpawns.json`, read and follow `Docs/raid_placement_id_numbering.md`.
- Use `Docs/save_persistence.md` to track gameplay/runtime state that must survive save/load. Update it whenever adding or changing persisted save data.
- For transparent PNG assets, use built-in image generation with native transparency. For outfit thumbnails, use the model captures as references to generate new illustrations. Do not use solid-background recoloring, black/white image pairs, or multi-image alpha extraction.
- For `Tools/QuestStudio` changes, after implementation and pre-deployment verification pass, commit and push the verified source before deploying with Wrangler. Report build/test and deployment-command results, but leave final acceptance of live behavior to the user; do not claim that deployed functionality is confirmed working on the user's behalf.
- Before editing quest authoring data, run `npm run quest:status -- --flavor Demo` or `Main` in `Tools/QuestStudio`. If the result is `pull-required`, run the matching `quest:pull` before editing. Run `quest:validate` after edits. Run `quest:push` only when the user explicitly requests publishing. Never copy the Main authoring pack into the public repository.

- Treat implementation, one-off generator cleanup, validation, and task logging as one unit of work and commit them together in a single task commit. For one-off editor asset-generation code, validate the generated assets, remove the generator, its entry points, and generator-only dependencies, then revalidate before that single commit. Do not create separate generator-cleanup or task-log commits, and do not leave completed asset generators or startup regeneration paths in the final source tree.
