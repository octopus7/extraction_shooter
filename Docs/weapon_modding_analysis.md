# 무기 모딩 현황 분석

조사일: 2026-09-26. 정식 구현 전 현황 조사이며 확정 설계가 아니다.
C++ 소스, 아이템 JSON/문자열 CSV, 기존 문서를 대조했다. 에디터에서 WBP 계층과 실제 플레이 화면은 확인하지 않았고 빌드·실행 테스트는 하지 않았다.

## 요약

부착물 장착·교체·분리, 호환 검사, 중첩 아이템 저장은 이미 구현되어 있다. 재사용할 기반이 충분하다. 정식화의 핵심은 부품 효과의 일관성, 무기 이동 시 상태 보존, 모딩 전용 UI 정보와 실패 안내다.

## 현재 사용자 흐름

1. 일반 아이템 슬롯에서 무기를 클릭하면 선택 아이템 상세 패널이 열린다. 상점에서는 판매 패널이 우선한다.
2. 선택한 아이템 정의에 `AttachmentSlotTags`가 있으면 상세 패널의 모딩 영역을 표시한다.
3. 부품을 모딩 슬롯에 드롭하거나, 일반 슬롯에 있는 호환 무기 자체에 드롭하여 장착한다.
4. 같은 슬롯에 기존 부품이 있으면 교환한다. 직접 무기 드롭 경로에서는 기존 부품이 원본 슬롯으로 돌아간다.
5. 장착 부품을 일반 슬롯으로 드래그해 분리한다. 대상 슬롯과 교환 부품의 수용 가능 여부를 검사한다.
6. 변경은 즉시 인벤토리 상태에 반영된다. 모딩 전용 적용/취소 트랜잭션은 없다.

모딩은 일반 인벤토리 이동 경로에 포함된다. 해당 경로에는 작업대·벙커 전용 제한, 작업 비용, 작업 시간이 없다.
무기 슬롯 아이콘에는 슬롯 태그 순서에 따른 `●/○` 장착 여부 표시가 있다.

## 구현 구조

| 영역 | 구현 |
| --- | --- |
| 정의 | `ItemTable.json`: 무기의 `attachment_slot_tags`, 부품의 `attachment_slot_tag`, `compatible_weapon_type_tags`, `magazine_capacity_bonus` |
| 소유 관계 | `FTunaSweeperItemInstance::AttachmentSlots`: 슬롯 태그 → 부품 UID. 부품도 `ItemInstancesByUid`의 독립 인스턴스 |
| UI 진입 | `SelectItemSlot` → 선택 변경 이벤트 → `RefreshSelectedItemInfo` |
| UI 편집 상태 | 현재 선택한 무기의 맵을 `SelectedWeaponAttachmentSlots` 배열로 투영하고, 이동 후 원래 무기 맵에 기록 |
| 호환 검사 | 슬롯 태그 일치 + 무기의 슬롯 존재 + 총종 호환. 호환 총종 목록이 비면 모든 총종 허용 |
| 장착 | 일반 `CanMoveItemBetweenSlots` / `MoveItemBetweenSlots` 내부에서 부품 직접 장착을 일반 스왑보다 먼저 처리 |
| 장탄수 | `CalculateWeaponMagazineCapacity`: 무기 기본 장탄수 + 장착된 부품의 장탄수 보너스 합 |
| 외형 | `ApplyEquippedWeaponAttachmentVisuals`는 현재 레이저 활성화만 처리. 임의 부품 메시·소켓을 조립하는 범용 경로는 확인되지 않음 |
| 무게 | 장착 부품 UID를 재귀적으로 따라가 소지 무게에 포함 |
| 저장 | 소유 무기에서 부품 UID를 재귀 수집하여 무기와 부품 인스턴스를 함께 저장. 벙커 변경은 UI 종료 후 저장하는 기존 정책 적용 |

선택 상태는 무기 UID가 아닌 슬롯 참조 중심이다. 전용 모딩 화면을 만들 때에는 화면을 연 뒤 무기 이동·선택 변경이 일어나도 편집 대상이 안정적으로 유지되도록 명시적인 무기 UID를 사용하는 편이 좋다.

## 정식화 전에 해결할 문제

아래는 소스에서 확인한 경로와 그로부터 도출한 영향이다. 실행 재현은 별도로 필요하다.

### 1. 무기 버리기에서 모딩 상태가 보존되지 않음 — 우선순위 높음

`PlayerController::HandleDrop`은 바닥 아이템에 ItemId와 Quantity만 넘긴다. `RemoveItemFromSlot`은 무기 아래 부품 인스턴스를 재귀 삭제한다. `PickupItemActor::SetItemStack`도 ID와 수량만 받는다.
따라서 이 경로에는 부품과 장전탄 상태를 바닥 아이템으로 이전하는 처리가 없다. 모딩된 무기를 버렸다가 다시 줍는 과정의 상태 보존이 필요하다.

### 2. 탄창 제거 후 초과 장전탄 손실 — 우선순위 높음

탄창 제거는 일반 부품 이동으로 처리하며 초과 탄약을 반환하지 않는다. 탄 수 조회는 새 용량으로 제한하고, 실제 사격/재장전에서는 `LoadedAmmoCount` 자체를 새 용량으로 제한한다.
예: 45발을 장전한 기본 소총에서 +15 탄창을 제거하면 조회는 30발로 내려가고 다음 사격에서 내부 수량도 30으로 줄인 뒤 1발을 소비한다. 초과 15발을 보존·반환하는 정책이 필요하다.

### 3. 모딩 슬롯의 툴팁 데이터 누락

`HudItemInfoPanelWidget::RefreshSelectedItemInfo`는 장착 부품 타일에 이름·아이콘·인스턴스만 채우고 `ItemDefinition`, `bHasItemDefinition`, `DescriptionText`를 채우지 않는다.
공통 호버 위젯은 이 필드로 무게·가격·설명을 표시하므로 모딩 슬롯에서는 무게/가격이 0, 설명이 빈 값으로 계산된다. 일반 슬롯과 동일한 타일 데이터 생성 경로를 재사용할 필요가 있다.

### 4. 호환 데이터와 실제 부품 효과가 다름

- 2026-09-26 수정: 레이저는 장착 부품의 `provides_laser_sight`와 무기 슬롯·호환 태그로 판정한다. 특정 아이템 ID나 소총 전용 조건 없이 호환되는 SMG에서도 사용할 수 있다.
- 레드닷은 장착 데이터만 확인된다. 어떤 효과를 부여할지 결정해야 한다.
- 탄창 보너스를 제외한 부품 공통 능력치 계산기가 없으며, 현재 상세 스펙 UI도 탄약 피해량과 방어구 방어력만 처리한다.

### 5. 판매·분해에서 장착 부품 취급이 미정

판매 가격은 무기 자신의 `ShopSellPrice × Quantity / 2`이고 부품 가치는 합산하지 않는다. 판매 시 무기 제거가 부품도 재귀 삭제한다. 작업대 아이템 소비도 부품을 재귀 삭제하는 경로를 가진다.
판매/분해 전 자동 분리, 부품 가치·분해 결과 포함, 장착 상태에서 처리 제한 중 어떤 정책인지 정해야 한다.

### 6. UI와 판정이 일반 인벤토리 동작에 강하게 결합됨

- C++의 부착물 드롭 위치 계산은 2열을 가정하고 타일 크기를 96×96으로 설정한다. 전용 화면으로 바꿀 때 레이아웃과 드롭 판정을 함께 변경해야 한다.
- 부품 호환 목록, 장착 전후 수치 비교, 부품 전용 효과 설명, 장착 불가 이유를 보여주는 모딩 전용 UI는 확인되지 않는다.
- 이동 실패는 bool/FString 중심이며 모딩 실패 이유를 현지화 키로 사용자에게 전달하는 흐름이 필요하다.
- 호환되지 않는 부품을 일반 무기 슬롯 위에 놓으면 부착 분기가 실패한 뒤 일반 이동/스왑 판정을 계속한다. 전용 모딩 화면에서는 의도하지 않은 무기·부품 자리 교환을 구분해야 한다.
- 기존 표시 코드에 fallback 리터럴과 알려지지 않은 슬롯 태그 직접 출력이 있다. 새 UI는 프로젝트의 문자열 키 규칙을 따라야 한다.

## 재사용할 부분과 권장 정비 순서

1. **아이템 상태 보존부터 검증**: 무기 버리기/줍기, 초과 탄약, 판매·분해, 저장/로드에서 부품과 탄약의 보존·소비 규칙을 확정한다.
2. **장착 규칙을 UI에서 분리**: 기존 UID 맵은 유지하고 무기 UID와 부품 UID를 명시하는 장착·분리·교체 API 및 공통 호환 판정을 둔다.
3. **효과 계산을 통합**: 확정된 부품 종류에 필요한 효과만 정의하고, 실제 전투와 UI 수치가 같은 계산 결과를 사용하게 한다.
4. **모딩 UI 완성**: 무기 정보, 슬롯명·장착 상태, 호환 부품과 효과, 변화량, 실패 이유를 표시한다. 일반 타일의 데이터/툴팁 생성은 재사용한다.
5. **회귀 검증 추가**: 장착/교환/분리, 호환 불가, 인벤토리 공간 부족, 모딩 중 대상 이동, 탄창 제거, 모딩된 무기 드롭/줍기, 저장/로드를 검증한다. 현재 검색에서는 이런 흐름을 직접 다루는 전용 테스트를 찾지 못했다. 데모 초기 레이저 장착을 확인하는 보스 테스트는 존재한다.

## 사용자 확인 방향과 남은 설계 질문

이번 대화에서 사용자는 같은 부위의 부품이 더 높은 등급일 수도 있고, 성능 우위가 아닌 기능 자체의 차이일 수도 있다고 명시했다. 따라서 정식 모딩은 등급에 따른 성장과 기능에 따른 선택을 모두 수용해야 한다. 모든 교체를 단순한 상위 부품 교체로 취급하지 않는다.

기존 `Docs/Steam/steam_indie_game_scope_summary.md`의 8장은 부품 획득으로 무기의 단점을 해소하는 장비 복구/강화 방향을 제안했지만, 동일 슬롯의 다양한 기능 선택을 피하라는 부분은 이번 사용자 설명과 다르다. 정식 설계에서는 이번 설명을 우선한다.

이 방향에서 필요한 것:

- 아이템의 기존 `ItemGrade`를 활용하되, 등급과 실제 효과를 별개 데이터로 취급한다. 높은 등급이라는 이유만으로 모든 효과가 우월하다고 표시하지 않는다.
- 같은 슬롯의 수치 효과와 기능 효과를 표현할 수 있어야 한다. 실제 전투·시각 효과·UI 설명이 같은 정의를 참조하도록 한다.
- 교체 비교는 장탄수 같은 숫자 변화와 기능 추가/제거를 함께 보여준다. 종합 점수 하나로 우열을 강제하지 않는다.
- 호환 판정과 효과 계산은 선택한 부품의 구체적인 정의에 따라 수행한다. 레이저는 `provides_laser_sight` 속성으로 일반화했으며, 후속 부품 효과도 같은 데이터 중심 원칙을 따른다.

남은 질문:

- 현재처럼 인벤토리에서 즉시 교체하는가, 벙커·작업대에서만 작업하는가?
- 정식 1차 범위는 현재 3종 부품의 효과·UI 완성인가, 새 슬롯·부품 추가까지인가?
