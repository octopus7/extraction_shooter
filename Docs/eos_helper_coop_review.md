# EOS 도움 코옵 설계 및 어뷰징 검토

- 검토일: 2026-09-16
- 대상: TunaSweeper / Unreal Engine 5.7
- 상태: 구현 전 검토. 아래 권장안은 확정된 구현 계약이 아니다.
- 목적: 진행 중인 싱글플레이 세이브 슬롯에 헬퍼가 참가하여 전투를 돕되, 아이템 거래와 진행 오염을 방지한다.

## 1. 사용자 요구사항과 해석

### 명시된 요구사항

- EOS를 사용한 도움 코옵 네트워크 플레이를 검토한다.
- 진행 중인 세이브 슬롯을 선택하여 플레이한다.
- 헬퍼는 루팅과 버리기를 할 수 없다.
- 헬퍼는 몸에 가져온 아이템만 사용·소모한다.
- 상자 넣기나 버리기를 통한 간접 거래도 금지한다.
- 호스트 사망 시 즉시 게임 종료 처리한다.
- 헬퍼 사망 시 이어하기를 허용하지 않는다.

### 이 문서의 해석과 미확정 사항

- 호스트의 게임 종료는 해당 출격의 플레이를 즉시 끝내고 저장·정산 후 결과 화면으로 이동하는 것으로 해석한다. 실행 프로세스 강제 종료로 해석하지 않는다.
- 헬퍼의 이어하기 금지는 해당 출격에서 부활·재참여할 수 없다는 의미로 해석한다. 원본 세이브 삭제나 장비 전손은 별도 정책이다.
- 호스트는 세계를 진행할 슬롯을 선택하고, 헬퍼는 반입 장비의 출처 슬롯을 선택하는 구조를 가정한다.
- 참가 인원, 중도 참가, 재접속, 장비 손실, 지원 효과, 보상은 아직 확정되지 않았다.

## 2. 권장 기본 구조와 신뢰 경계

호스트 PC가 서버 역할도 수행하는 리슨 서버를 기본 후보로 삼는다. EOS는 인증·초대·온라인 연결을 담당하고, UE의 서버 권한 로직이 전투·아이템·사망·탈출을 판정한다. EOS를 연결해도 게임 규칙이 자동으로 동기화되거나 검증되지는 않는다. [UE 5.7 네트워킹 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine?application_version=5.7)

| 데이터 및 행동 | 권장 소유권과 권한 |
|---|---|
| 세계·적·상자·퀘스트·탈출 상태 | 호스트 서버가 소유하고 판정 |
| 호스트 영구 진행 | 선택한 호스트 슬롯에만 저장 |
| 헬퍼 원래 세계·퀘스트 | 호스트 진행을 복사하지 않음 |
| 헬퍼 장비 | 참가 시 확정한 반입 목록을 기준으로 독립 관리 |
| 헬퍼 인벤토리 정리·장비 교체 | 자기 소유 영역 안에서 허용 |
| 헬퍼 아이템 획득·외부 이전 | 금지 |
| 대화 선택·납품·탈출·맵 이동 | 호스트만 결정 |

서버 요청마다 인증된 행동 주체, 역할, 출격 상태, 소유권, 수량, 거리와 대상 유효성을 검사한다. 클라이언트가 전달한 아이템 수치·피해량·성공 결과를 그대로 신뢰하지 않는다. UI 비활성화와 서버 검증을 함께 적용한다.

리슨 서버의 호스트 자체는 플레이어가 통제한다. 로컬 세이브 편집·백업 복원·악성 호스트까지 완전히 방어하려면 별도의 신뢰할 수 있는 서버 측 상태 관리가 필요하다. 초기 목표는 정상 클라이언트에서의 우회·복제 방지와 악성 참가자의 영향 제한으로 잡는 것이 현실적이다.

## 3. 거래 및 간접 이전 차단

핵심 원칙: **헬퍼 반입품은 사용·소모될 수 있지만 호스트 소유의 아이템으로 전환될 수 없다.**

| 우회 경로 | 필요한 방어 |
|---|---|
| 바닥 버리기·상자 보관 | 외부 컨테이너로의 이동을 서버에서 거절 |
| 사망 시 시체·가방 생성 | 회수 가능한 헬퍼 아이템을 월드에 남기지 않음 |
| 가방 해제·장비 교체로 공간 초과 | 자동 바닥 배출 금지, 작업 거절 또는 내부 보관 정책 적용 |
| 총·탄창·장전탄·탄 빼기 | 탄약에도 동일한 소유권 검사 적용 |
| 부착물 탈착·분해 | 파생 부품과 결과물에 소유권 유지 |
| 제작대·수리대·공용 재료함 | 헬퍼 재료의 외부 투입 및 결과물 이전 금지 |
| 판매 후 호스트 재구매 | 헬퍼 상점 판매 및 매입함 경유 금지 |
| 우편·자동 습득·보상함 | 직접 루팅과 동일한 획득 제한 적용 |
| 투척 무기·화살·함정·설치물 회수 | 호스트가 헬퍼 물체를 아이템화하지 못하게 함 |
| 퀘스트 납품·시설 수리 | 헬퍼 반입품으로 호스트 재료 조건을 대신 충족하지 못하게 함 |
| 펫·드론 자동 수집 | 소환 주체의 권한을 따라가도록 처리 |

아이템 UID뿐 아니라 소유자와 반입 출처를 추적해야 한다. 스택 합치기·분할, 중첩 가방, 장착 부품에도 소유권이 유지되어야 한다. 헬퍼 소유품과 호스트 소유품이 하나의 스택으로 섞이지 않게 한다.

### 지원 효과의 경계

회복약을 호스트에게 사용하면 물건은 이전되지 않지만 회복 자원을 제공한다. 다음 중 정책 선택이 필요하다.

- 엄격한 제한: 자기 회복·자기 버프만 허용.
- 지원 허용: 타인 회복·버프는 허용하되 헬퍼 자원을 실제 차감.
- 설치형 탄약·보급함은 거래 우회성이 높으므로 별도 제한.

헬퍼가 적을 처치하고 호스트가 전리품을 얻는 것은 정상적인 전투 도움으로 볼 수 있다. 자원 지원과 진행 조건 대행의 허용 범위를 명시해야 한다.

## 4. 출격·참가 이력과 재접속

방을 다시 만드는 것만으로 이력이 초기화되지 않도록 방 ID와 별개의 출격 ID를 둔다.

| 악용 | 권장 방어 |
|---|---|
| 탄약 소비 후 재입장으로 보급 | 기존 체력·탄약·내구도·위치를 복구하고 새 반입 목록을 받지 않음 |
| 사망 후 다른 슬롯으로 재입장 | 인증된 계정 기준으로 해당 출격 재참여 금지 |
| 사망 직전 연결 끊기 | 연결 종료 즉시 캐릭터 제거·무적 적용 금지 |
| 헬퍼 무한 교대 | 출격 중 참가자 교체 제한, 벙커 복귀 후 교체 권장 |
| 방 재생성으로 이력 초기화 | 같은 출격을 재개하면 참가·사망 이력 유지 |
| 같은 장비를 여러 출격에 동시 반입 | 참가 중 출처 슬롯 및 반입품 사용 잠금 |

재접속 허용 시간, 끊긴 캐릭터의 잔존 시간과 행동, 제한 시간 만료 결과를 정해야 한다. 재접속은 기존 참가자의 복귀여야 하며 새 생명·새 장비를 제공하면 안 된다. 다른 계정 사용까지 로컬 정책만으로 완전히 차단할 수는 없다.

## 5. 사망·탈출·종료 처리

### 호스트 사망

1. 서버에서 출격 상태를 종료로 확정한다.
2. 새 공격·루팅·보상·탈출 요청을 차단한다.
3. 호스트 사망 저장을 수행한다.
4. 헬퍼 소비와 결과를 정산한다.
5. 결과 통지 후 연결을 종료한다.

종료 이후 도착한 탈출 요청이나 진행 보상으로 결과가 성공으로 바뀌면 안 된다. 사망과 탈출이 경합하면 서버 확정 순서를 사용하고, 같은 처리 단위에서 충돌할 경우의 우선순위를 정한다. 결과 확정은 한 번만 가능해야 한다.

저장 실패 시에도 전투는 재개하지 않는다. 종료 결과를 확정한 채 저장 재시도·복구가 가능해야 하며, 실패를 성공 저장으로 표시해서는 안 된다. 네트워크 연결 종료를 무한히 지연하지 않도록 미정산 상태를 별도로 복구할 수 있어야 한다.

### 헬퍼 사망

- 해당 출격에서 리스폰·부활·재접속 부활을 허용하지 않는다.
- 회수 가능한 시체 아이템을 생성하지 않는다.
- 관전을 제공하면 호스트 시점 중심으로 제한한다. 자유 카메라로 벽 너머 적과 상자를 탐색할 수 없게 한다.
- 사망 전에 발사한 탄환·설치한 함정의 효과 유지 여부는 별도 결정한다.

### 연결 종료와 강퇴

- 헬퍼 연결 종료 시 호스트는 계속 진행할 수 있다.
- 호스트 연결 종료 시 해당 호스트 세계를 다른 참가자가 이어받지 않는 방향을 권장한다.
- 정상 이탈·강퇴·통신 장애·프로세스 충돌을 구분해 기록한다. 기록만으로 고의 여부를 확실히 판별할 수는 없다.
- 강퇴나 통신 장애를 곧바로 장비 전손으로 처리하면 악성 호스트의 피해 유발 수단이 된다.

## 6. 헬퍼 손실 및 보상 정책

초기 권장안은 **실제 사용한 탄약·소모품과 내구도 감소를 부담하고, 사망 시 해당 출격에서 퇴장하되 장비 전체 몰수는 적용하지 않는 방식**이다. 이는 제안이며 사용자 확정 규칙이 아니다.

루팅 보상이 없는 헬퍼에게 호스트의 실수·고의 사망·강퇴까지 장비 전손으로 부담시키면 참여 동기가 약해진다. 전손을 채택한다면 아래 사건별 결과를 먼저 정의해야 한다.

| 사건 | 결정할 항목 |
|---|---|
| 헬퍼 자신의 전투 사망 | 장비·소모품 손실 범위 |
| 헬퍼 생존 중 호스트 사망 | 잔여 장비 반환 여부 |
| 헬퍼 자진 이탈 | 소비 정산과 추가 페널티 여부 |
| 호스트 강퇴 | 소비 정산과 피해 방지 |
| 통신 장애·충돌 | 재접속 및 미정산 복구 |
| 정상 탈출 | 잔여 반입품 반환, 보상 유무 |

지원 보상을 추가하면 무참여 보상, 반복 짧은 출격, 다중 계정, 보상 직전 강퇴를 검토해야 한다. 처치·퀘스트·업적을 무조건 양쪽 계정에 지급하지 않는다.

## 7. 저장·정산과 복제 방지

대표 실패 사례: 헬퍼가 탄약 100발 중 80발을 사용한 뒤 결과 저장 전에 종료하여, 기존 세이브의 100발을 다시 사용한다.

필요한 설계 요소는 다음과 같다.

- 참가 전 출처 슬롯과 반입 장비 목록·수량 확정.
- 참가 중 원본 슬롯 및 반입품 중복 사용 제한.
- 미정산 출격 기록과 소비 기록 유지.
- 정산 고유 번호와 적용 여부 기록으로 재전송·재시도 시 중복 차감 방지.
- 정상 종료뿐 아니라 강제 종료 후에도 미정산 기록 복구.
- 저장 실패·클라우드 충돌·과거 백업 복구 처리.
- 호스트가 보낸 결과를 헬퍼의 전체 세이브 덮어쓰기 명령으로 사용하지 않음. 해당 출격과 반입품 범위의 변화만 검증하여 적용.

현재 [저장 계약](save_persistence.md)의 CRC와 이전 세대 복구는 파일 손상 대응 장치다. 악의적 세이브 편집이나 과거 파일 복원을 방지하는 인증 장치가 아니다. 두 PC의 로컬 저장도 하나의 원자적 트랜잭션이 되지 않는다.

미정산 기록과 중복 적용 방지는 정상적인 장애 복구를 개선하지만, 신뢰할 수 없는 두 클라이언트 사이의 경제 무결성을 보장하지는 않는다. 엄격한 경제 보호가 필요하면 서버 측 장비·소비 관리가 필요하다.

이 문서는 저장 필드를 추가하지 않는다. 실제 구현 시 출격·참가·사망·미정산 데이터 중 영속화할 항목을 확정하고 `save_persistence.md`와 버전 이행 정책을 함께 갱신해야 한다.

## 8. 전투·진행·정보 악용

| 분야 | 위험 | 권장 검토 |
|---|---|---|
| 고급 장비 캐리 | 초반 난이도와 진행 조건 무력화 | 반입 등급·전투 수치 제한 필요 여부 |
| 적 유인 | 적을 멀리 끌어 호스트의 무위험 루팅 지원 | 추적 범위·복귀·경계 상태 |
| 몸막기 | 통로·문·탈출구 봉쇄 | 플레이어 간 충돌·밀치기 제한 |
| 팀킬 | 폭발·불·낙하 유도 포함 | 직접·간접 아군 피해 정책 |
| 중요 NPC·시설 파괴 | 진행 불가 상태 유발 | 진행 관련 파괴 권한 |
| 진행 강제 변경 | 대화·보스 시작·탈출 강요 | 호스트 전용 결정 |
| 참가 인원 변화 | 보스 체력·보상 재계산 악용 | 전투 중 배율 변경 방식 또는 고정 시점 |
| 보상·업적 | 양쪽 중복 지급과 반복 파밍 | 처치 주체와 진행 소유자 분리 |
| 관전 | 사망자의 정찰·스포일러 | 시점·대상 정보 제한 |
| 불필요한 상태 전송 | 미개봉 상자와 미발견 적 정보 추출 | 필요한 정보만 참가자에게 전송 |
| 과도한 요청 | 상호작용·발사 요청으로 서버 부하 | 빈도·수량·거리·상태 검사 |

헬퍼가 도움을 주어 플레이가 쉬워지는 것은 모드의 목적이다. 모든 이득을 악용으로 간주하지 말고, 허용할 도움과 금지할 진행 건너뛰기를 구분한다.

## 10. EOS 통합 및 운영 확인 사항

UE 5.7 OSS EOS는 온라인 서비스와 플레이어 호스팅용 P2P 소켓 구성을 제공한다. EOS Connect와 Epic Account Services 로그인은 구분하여 검토하고, 실제 배포 플랫폼에 맞는 인증·초대 구성을 선택한다. [UE 5.7 OSS EOS 공식 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/online-subsystem-eos-plugin-in-unreal-engine?application_version=5.7)

- 표시 이름이나 클라이언트가 주장한 ID 대신 인증된 사용자 ID로 참가 기록을 관리한다.
- 초대·로비 참가뿐 아니라 실제 게임 서버 입장 시 권한을 검사한다.
- 로비 소유자 변경을 게임 호스트와 세이브 권한의 자동 승계로 취급하지 않는다.
- Demo/Main, 프로토콜·게임·데이터 버전 호환성을 입장 전에 검사한다.
- Steam·Stove 등 배포 채널별 인증 지원과 초대 흐름은 별도 확인한다. 모든 플랫폼이 같은 구성으로 동작한다고 가정하지 않는다.
- 개발·테스트·출시 환경을 구분하고 필요한 서비스 권한만 부여한다.
- 방화벽·공유기·릴레이 경유·지연·패킷 손실·연결 복구를 실제 다른 PC 환경에서 검증한다.
- EOS 로그인 실패나 서비스 장애가 오프라인 싱글플레이를 막지 않게 한다.
- 안티치트 사용 여부와 관계없이 아이템·피해·사망 규칙은 서버에서 검증한다.

## 11. 첫 버전 권장 범위

- 호스트 1명과 초대 헬퍼 1명.
- 출격 전에 참가자와 반입품 확정, 출격 중 참가자 교체 금지.
- 호스트만 루팅·납품·퀘스트 선택·탈출 결정.
- 헬퍼는 반입품 사용과 전투만 가능.
- 헬퍼 사망 시 해당 출격 재참여 금지, 호스트 사망 시 출격 종료.
- 헬퍼의 원래 세계 진행도는 변경하지 않음.
- 실제 소비 및 내구도 감소만 정산하는 정책을 우선 검토.
- 재접속을 지원한다면 기존 상태 그대로 복구.

### 구현 전에 확정할 결정

1. 헬퍼 장비 전손 여부와 사건별 손실 범위.
2. 타인 회복·버프·설치물 등 지원 효과 허용 범위.
3. 중도 참가와 재접속 시간, 연결이 끊긴 캐릭터 처리.
4. 헬퍼 경험치·업적·지원 보상 유무.
5. 사망과 탈출 경합 우선순위 및 미정산 복구 정책.
6. 전투 난이도 보정과 고급 장비 반입 제한 여부.
7. 코옵에서의 일시정지·슬로모션 정책.

## 13. EOS 적용 시 리플리케이션 구현 범위

리플리케이션은 서버가 가진 게임 상태를 각 클라이언트에 전달하는 기능이다. EOS 연결 설정과 별도로 구현해야 한다. 다음은 프로젝트 소스의 정적 확인과 UE 5.7 문서를 바탕으로 한 작업 목록이며, Blueprint 기본값과 실제 두 클라이언트 실행까지 검증한 결과는 아니다.

### 13.1 이미 존재하는 구현과 우선 감사 대상

| 현재 확인된 코드 | 의미 및 추가 작업 |
|---|---|
| `VitalsComponent`의 `SetIsReplicatedByDefault`, `DOREPLIFETIME`, `OnRep` 및 서버 권한 Tick | 체력·식량·수분 동기화의 기반이 있음. 소유 액터의 복제 설정, 초기 상태, 사망 호출, 공개 범위를 함께 검증 |
| `DebuffComponent`의 배열 복제와 Server RPC | 기존 기반을 재사용하되 임의 적용·해제 요청이 정당한 아이템 사용 또는 전투 결과인지 검증해야 함 |
| `BurnComponent`의 연소 여부·스택 복제와 적용 시 권한 검사 | 연소 시각 효과, 늦은 참가, 사망 후 효과 종료, 처치 기여 주체 검증 |
| `CombatPatternEffectActor`의 `bReplicates = false` | 시각 전용 액터 자체는 로컬 생성 가능. 서버가 확정한 공격 시작·방향·시간을 전달받아 같은 패턴을 표현하는 경로 필요 |
| `Weapon`의 투사체 생성 경로 | 서버가 유일한 판정용 투사체를 생성하도록 호출 경로 감사 |
| `LevelTransitionSubsystem`의 `OpenLevel` | 연결을 유지하는 코옵 이동에는 서버 주도 travel 흐름이 별도로 필요 |
| 기본 `GameMode`의 Pawn·Controller 클래스 설정 | 출격 상태와 참가자 역할을 관리할 GameState·PlayerState 설계 추가 필요 |

특히 `ServerTryApplyDebuff`는 클라이언트 인자로 효과 ID·확률 보너스·시간 보너스·SourceActor를 받고, `ServerRemoveDebuff(s)`는 내부 제거 함수를 호출한다. 코옵에서 접근 가능한 경우를 감사하고, 서버가 승인한 치료·전투 행동에서 효과를 계산하도록 바꿔야 한다. 단순히 Server RPC라는 이유만으로 요청 내용이 신뢰 가능한 것은 아니다.

컴포넌트가 복제를 선언해도 소유 액터의 복제가 활성화되어 있어야 한다. 액터·컴포넌트 설정과 실제 네트워크 소유권을 함께 검사한다. [UE 5.7 컴포넌트 복제](https://dev.epicgames.com/documentation/en-us/unreal-engine/replicating-actor-components-in-unreal-engine?application_version=5.7)

### 13.2 데이터 배치와 전달 대상

| 위치 | 맡길 상태 | 전달 범위 |
|---|---|---|
| GameMode | 참가 승인, 호스트·헬퍼 권한, 사망·탈출 판정 | 서버 전용 |
| GameState | 출격 단계·ID, 종료 결과, 공용 목표 요약, 서버 기준 시각 | 참가자 공용 |
| PlayerState | 참가자 역할, 생존·탈락 상태, 공개 장비 요약 | 필요한 참가자에게 공개 |
| 소유 Pawn/Controller의 인벤토리 컴포넌트 등 | 아이템 UID·수량·탄약·내구도·소유권 | 서버와 해당 소유 클라이언트 |
| Pawn 및 전투 컴포넌트 | 이동·조준·장착 상태·공개 체력·행동 상태 | 관련성이 있는 참가자 |
| 서버 저장 서비스/GameInstance | 호스트 영구 저장, 출격 및 정산 기록 | 세이브 전체를 복제하지 않음 |
| 로컬 UI·카메라 | 설정, 커서, 카메라 흔들림, 현지화 문구 | 각 클라이언트 로컬 |

GameInstance는 자동으로 공유·복제되는 저장 공간이 아니다. 기존 아이템 함수를 참가자별 소유 상태를 받는 구조로 분리해야 한다. PlayerController 역시 다른 모든 참가자에게 존재하는 공용 저장소로 사용하면 안 된다. 아이템 데이터 정의는 공통 ID와 버전으로 맞추고, 네트워크에는 인스턴스의 필요한 변화만 전달한다.

| 퀘스트·시설·탈출 | 호스트 권한 및 진행 조건, 탈출 카운트다운 | 목표 요약·상호작용 가능 여부·남은 시간 | 헬퍼 진행 저장과 납품 대행 방지 |
| 사운드·VFX·애니메이션 | 게임 결과와 필요한 연출 이벤트만 확정 | 로컬 연출 생성·재생 | 탄피·피해 숫자를 불필요한 복제 액터로 만들지 않음 |

일반 이동은 CharacterMovement의 기존 네트워크 예측·보정을 우선 사용한다. 커스텀 구르기나 이동 속도 변경이 예측에 영향을 주면 해당 입력 상태를 서버 이동 재현에 포함해야 한다. transform을 매 프레임 별도 Reliable RPC로 보내는 방식은 피한다.

발사 입력은 빠르게 로컬 연출할 수 있지만 실제 탄약·피해는 서버가 확정한다. 예측 연출과 서버 확정 연출을 같은 발사 ID로 연결하여 이중 재생을 막는다. 고속 투사체는 서버 궤적 판정과 클라이언트 시각 표현을 분리할지 검토한다. 지연 보상은 허용 시각 범위를 제한하며 과거 명중 주장만으로 피해를 주지 않는다.

### 13.4 RPC 설계 원칙

RPC는 다른 머신에서 함수를 실행하도록 보내는 요청이며 반환값이 없는 비동기 호출이다. 호출이 전달될지는 네트워크 소유권과 RPC 종류에 영향을 받는다. [UE 5.7 RPC 공식 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine?application_version=5.7)

- 헬퍼가 소유하지 않은 상자 액터에 직접 Server RPC를 호출하지 않는다. 소유 Controller/Pawn을 통해 대상과 행동을 요청하고 서버가 권한·거리·상태를 검증한다.
- 요청에는 행동 의도를 담는다. 클라이언트가 최종 피해량·보상 수량·아이템 소유자·생존 여부를 정하지 않는다.
- 거래·장비 변경처럼 드문 중요 요청은 신뢰성 있는 전달과 요청 ID를 사용한다. 재접속·앱 재시도에 대한 중복 적용 방지는 별도로 구현한다.
- 조준과 반복 시각 효과에는 손실을 허용할 수 있는 전달 또는 상태 복제를 검토한다. 매 프레임 Reliable 호출로 큐를 채우지 않는다.
- 지속 상태를 Multicast 이벤트 하나로만 표현하지 않는다. 늦게 접속하거나 관련 범위에 다시 들어온 클라이언트도 현재 상태로 복원할 수 있어야 한다.
- 서로 다른 액터의 RPC·속성 도착 순서에 의존하지 않는다. 출격 ID·상태 버전·결과 ID로 오래된 요청과 중복 이벤트를 거절한다.
- 입력 파라미터의 범위, 배열 길이, 유효 아이템 ID, 요청 빈도를 검사한다.

### 13.5 초기 동기화·맵 이동·관전·재접속

1. 참가 승인 후 호스트의 세계 상태와 참가자 상태를 준비한다.
2. 반입품 검증과 로드아웃 확정이 끝나기 전에는 조작을 허용하지 않는다.
3. 서버가 Pawn을 생성하고 올바른 Controller에 소유시킨다.
4. UI는 필요한 복제 상태가 준비된 뒤 표시하며, 액터 참조가 아직 도착하지 않은 경우를 처리한다.
5. 재접속 시 새 참가자 생성 대신 출격 참가 기록에 연결하고 사망 여부를 먼저 검사한다.
6. 맵 이동은 서버 주도로 처리한다. Seamless Travel 사용 여부와 PlayerState·인벤토리 이전·초기화 범위를 정한다.
7. 사망 관전으로 바뀌어도 탈락 이력은 Pawn 수명과 무관하게 유지한다.

호스트의 `OpenLevel`을 그대로 호출하면 연결과 참가 상태가 끊길 수 있다. 기존 페이드·로딩·벙커 복귀 저장과 서버 travel 완료·실패를 하나의 상태 흐름으로 정리해야 한다. 호스트 종료 결과는 최종 네트워크 알림만 믿지 말고 정산 기록과 함께 복구 가능하게 한다.

### 13.6 복제량·공개 범위·타이머

- 전체 세이브나 전체 아이템 맵을 모든 참가자에게 전송하지 않는다.
- 큰 인벤토리는 항목별 변경 전송 구조를 검토한다. Fast Array 등 구체 기술은 선택한 복제 시스템과 UE 5.7 호환성을 확인한 뒤 적용한다.
- 정적인 상호작용 액터는 관련 범위와 dormancy를 검토하고, 상태 변경 시 갱신이 누락되지 않도록 한다.
- OwnerOnly와 액터 관련성은 정보 전달 범위를 줄이는 수단이며 서버 권한 검증을 대체하지 않는다.
- 디버프 남은 시간을 매 Tick 배열 전체 변경으로 전달하기보다 서버 기준 만료 시각과 상태 변경을 보내는 방식을 검토한다.
- 카운트다운·보스 패턴은 서버 기준 시작·종료 시각으로 표시하고, 로컬 슬로모션과 혼동하지 않는다.
- Replication Graph나 Iris 도입은 필수 선행 조건으로 두지 않는다. 먼저 정확성을 확보하고 측정 결과로 필요성을 판단한다.

### 13.7 권장 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | EOS 인증·입장과 역할·출격 상태 | 두 PC에서 호스트·헬퍼 구분, 잘못된 버전·초대 거절 |
| 2 | 참가자별 상태 분리와 이동 | 두 캐릭터가 독립 소유 상태로 이동·구르기하고 호스트 저장을 오염시키지 않음 |
| 3 | 전투·AI·체력·사망 | 호스트와 헬퍼 모두 전투 가능, 피해·소비·사망 한 번 적용 |
| 4 | 인벤토리·상호작용 권한 | 직접 RPC를 통한 금지 행동까지 거절 |
| 5 | 탈출·맵 이동·저장·재접속 | 상태와 결과 유지, 중복 정산·부활 우회 없음 |
| 6 | 연출·대역폭·장애 대응 | 지연·패킷 손실에서 상태 수렴, UI 복구, 통신량 측정 |

검증에는 호스트/헬퍼 양쪽 시점, 다중 프로세스 및 실제 두 PC, 지연·손실·연결 단절, 초기 동기화, 관련 범위 재진입을 포함한다. 단일 PIE에서 이동이 보이는 것만으로 리플리케이션 완료로 판단하지 않는다. 기존 오프라인 싱글플레이 회귀 검증도 필요하다.

## 14. 결론

EOS 도움 코옵의 핵심은 연결 자체보다 **아이템 소유권 분리, 출격 단위 참가 이력, 사망 결과의 단일 확정, 장애에 견디는 소비 정산**이다. 이 경계를 먼저 정한 뒤 작은 참가 규모로 검증하는 것이 적합하다. 게임 코드와 현행 저장 계약은 이번 검토에서 변경하지 않았다.
