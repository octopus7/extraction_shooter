# 범용 의상 텍스처 디자인 플러그인 설계

작성일: 2026-11-12. 대상: Unreal Engine 5.7. 상태: 구현 전 검토용 설계.

준비된 의상 모델에 직접 그림을 그려 저장하고, 독립 캐릭터에 상의·하의 또는 한 벌 의상으로 장착하는 플러그인이다. 체형, 의상 형태, 그림 데이터를 분리해 새로운 캐릭터 비율을 추가할 때 편집기와 장착 로직을 다시 작성하지 않도록 한다. 첫 캐릭터는 동물의 숲을 참고한 큰 머리와 짧은 팔다리 비율로 준비한다.

이번 산출물은 설계 문서다. 모델링, 플러그인 코드, Widget Blueprint, 맵과 기존 세이브 변경은 구현 단계의 산출물이다.

## 1. 확정 요구와 설계 기본안

### 사용자가 확정한 요구

- 옷의 입체 형태는 미리 준비한 프리셋을 사용하고 텍스처를 직접 디자인한다.
- 사용자 디자인 텍스처는 옷 하나당 전체 64×64 한 장으로 통일한다. 여러 부위가 이 한 장을 나눠 쓰며 부위별 텍스처·그림 파일을 따로 관리하지 않는다.
- 하의도 디자인할 수 있다.
- 상의와 하의는 따로 장착한다. 한 벌 의상은 두 슬롯을 함께 차지한다.
- 현재 플레이어 캐릭터 전용 비율에 묶이지 않는 범용 구조를 사용한다.
- 최초 신체 비율은 동물의 숲과 유사한 방향으로 잡는다.
- 기존 플레이어와 독립적인 캐릭터를 구성한다.
- 이번 논의는 기능과 구조에 집중한다. 방송 진행, 전투, 보상, 입수 조건은 다루지 않는다.

### 이번 설계에서 제안한 기본값

아래 항목은 확정 규격과 설계자가 구체화한 기본안을 정리한 것이다. 옷 전체 64×64 한 장은 사용자 확정 사항이며, 그 외 아직 확정하지 않은 기본안은 구현 전 검토에서 조정할 수 있다.

| 항목 | 기본안 |
|---|---|
| 플러그인 작업명 | GarmentDesigner |
| 범용 대응 | 체형 프로필과 체형별 의상 모델을 등록하고, 동일한 의상 그림 규격을 공유 |
| 최초 체형 | StylizedCompact, 약 3등신, 기준 키 100cm의 스타일화된 이족 캐릭터 |
| 최초 옷본 | 상의 3종, 하의 3종, 한 벌 2종으로 총 8종 |
| 그림 해상도 | 옷 전체 64×64 한 장. 상의·하의는 각각 한 장, 한 벌 의상도 전체 한 장 |
| 그림 형식 | 불투명 RGB8 단일 이미지. 부위는 같은 이미지 안의 이름 붙은 영역 |
| 편집 방식 | 단일 캔버스의 전체 보기·부위 선택 편집과 독립 캐릭터의 3D 미리보기 |
| 기본 저장 | 게임 진행 슬롯과 독립된 디자인 라이브러리와 독립 캐릭터 외형 기록 |
| 최초 실행 범위 | 로컬 독립 캐릭터와 편집기. 원격 외형 전달용 데이터 계약을 함께 정의 |

최초 구현에는 플러그인 예제 맵과 현재 프로젝트의 현지화 연결용 어댑터를 포함한다. 플레이어 상호작용·기존 HUD 진입점·플레이어 세이브 연결은 포함하지 않는다. 예제 맵을 직접 열어 기능을 검증한다.

독립 캐릭터는 외형을 표시하는 대상이다. 이동·조작·AI를 요구하지 않는다. 기존 플레이어의 체형, 애니메이션, 장비, 저장 슬롯을 자동으로 교체하거나 연동하지 않는다.

## 2. 기존 프로젝트에서 확인한 조건

- [현재 의상 카탈로그](../../../TunaSweeper/Source/TunaSweeper/Public/Character/TunaSweeperOutfitCatalog.h)는 OutfitId에 몸체·의상 메시와 표시 문자열 키를 연결한다.
- [현재 의상 컴포넌트](../../../TunaSweeper/Source/TunaSweeper/Private/Component/TunaSweeperOutfitComponent.cpp)는 ATunaSweeperTopDownCharacter에 직접 의존하며 원본 스켈레톤과 본 구성이 같은 메시를 요구한다. 새 범용 플러그인의 기반 클래스로 사용하지 않는다.
- [기존 아이콘 편집기 설계](2026-11-09-icon-editor-design.md)는 픽셀 초안, 확정·취소, 저장 실패 시 원본 유지, 실제 WBP의 편집 가능한 트리라는 참고 사례다. 한 개의 32×32 아이콘 저장 형식과 현재 게임의 모달 처리를 의상에 그대로 적용하지 않는다.
- [UI 문자열](../../../TunaSweeper/Content/Data/UITextStrings.csv)과 문자열 키 해석 흐름을 유지한다. 플러그인 코어에서 현재 게임 인스턴스나 텍스트 서브시스템을 직접 참조하지 않는다.
- [저장 현황](../../save_persistence.md)의 현재 플레이어 SelectedOutfitId와 전역 의상 해금 데이터는 별개다. 새 디자인을 기존 해금 목록이나 플레이어 의상 ID로 취급하지 않는다.
- UE 5.7, cm 단위와 [프로젝트 기준](../../game_conventions.md)을 따른다. 실제 에디터 작업에 들어갈 때 [에디터 조정 규칙](../../unreal_editor_coordination.md)을 먼저 따른다.

## 3. 검토한 접근 방식

| 방식 | 장점 | 제약 | 이번 설계 |
|---|---|---|---|
| 공통 스켈레톤과 하나의 옷 모델을 스케일·모프 변형 | 가까운 체형끼리 적은 에셋으로 대응 | 큰 비율 차이, 옷의 두께와 관통, 각 체형의 모프 관리가 어려움 | 향후 한 체형 계열 내부의 확장 수단 |
| 체형 프로필마다 맞는 의상 메시를 준비하고 그림 규격 공유 | 서로 다른 비율과 스켈레톤에 대응하며 결과를 직접 검증 가능 | 지원 체형마다 의상 모델과 스키닝 작업이 필요 | 설계 기본안 |
| 임의 메시의 실행 중 자동 피팅 | 자동화가 잘 되면 모델 재사용 범위가 넓음 | 변형, 스키닝, 관통 해결이 별도의 큰 기능이 됨 | 최초 범위에서 제외 |

범용성의 계약은 “체형별 에셋을 등록하면 같은 편집·저장·장착 기능을 쓴다”이다. 임의 캐릭터에 기존 옷 메시를 무조건 맞추는 기능은 포함하지 않는다. 애니메이션 리타기팅만으로 옷의 체형 맞춤이 해결된다고 가정하지 않는다.

## 4. 데이터와 책임 분리

| 개념 | 책임과 주요 데이터 |
|---|---|
| BodyProfile | 안정적인 ProfileId와 버전, 몸체 메시·스켈레톤·기준 포즈, 기본 외형, 숨길 수 있는 신체 영역, 미리보기 애니메이션 |
| GarmentPreset | 안정적인 PresetId, Top/Bottom/FullBody 구분, PatternSchema 참조, 기본 그림, 표시 문자열 키 |
| GarmentFit | PresetId와 ProfileId에 맞는 의상 메시, 포즈 결합 정보, 신체 가림 영역, 착용 조합 호환 정보 |
| PatternSchema | SchemaId와 버전, 64×64 안의 편집 영역 ID·범위·유효 픽셀 마스크, 고정 UV 배치, 경계·여백 대응, 좌우 복사 변환, 표시 키 |
| DesignRevision | DesignId, 불변 Revision, PresetId, SchemaId·버전, 단일 64×64 RGB 이미지, 사용자 지정 이름, 내용 해시 |
| AppearanceSnapshot | CharacterId, ProfileId·버전, 상태 Revision, 장착한 의상의 정확한 DesignId·Revision 참조 |
| EditSession | 원본 참조, 임시 픽셀, 선택 색·부위, 실행 취소 내역, 미리보기 상태. 저장하지 않는 작업 상태 |

BodyProfile, GarmentPreset, GarmentFit, PatternSchema는 콘텐츠 제작자가 만드는 에셋이다. DesignRevision과 AppearanceSnapshot은 실행 중 저장되는 값 데이터다. 저장 파일과 네트워크 계약에서 UObject 포인터나 에디터 에셋 경로를 신원으로 쓰지 않는다. 안정적인 ID를 에셋 레지스트리에 대응시킨다.

PresetId는 의상의 형태, DesignId는 사용자가 만든 디자인의 신원이다. 같은 티셔츠 옷본으로 여러 DesignId를 만들 수 있다. Revision은 저장할 때 증가하며 기존 Revision의 내용은 바뀌지 않는다. 디자인을 수정해도 이미 장착한 다른 캐릭터가 자동으로 새 버전을 입지는 않는다.

## 5. 독립 캐릭터와 체형 확장

### 기본 구성

독립 예제 캐릭터는 일반 Actor와 몸체 포즈 소스, 외형 컴포넌트로 구성한다. 플러그인 코어는 ACharacter 상속이나 플레이어 컨트롤러·소유권·Possess를 요구하지 않는다. 미리보기 UI가 카메라와 대상 Actor 참조를 받아 회전·확대·축소한다.

첫 BodyProfile은 약 3등신을 목표로 한 독자적인 스타일화된 캐릭터다. 정확한 머리 크기·얼굴·팔다리 곡선은 모델링 단계에서 정하되 전체 비율은 에셋에 두고 코드의 상수로 사용하지 않는다. 초기에는 기본 얼굴·머리·손·발을 제공하고, 얼굴 조형·머리카락 편집은 별도 기능으로 남긴다.

전체 Actor의 균일 확대·축소는 허용한다. 키·팔다리·몸통을 개별 슬라이더로 바꾸는 체형 편집기는 최초 범위가 아니다. 새 비율은 새 BodyProfile로 추가한다.

### 의상 맞춤 계약

1. 한 BodyProfile 안에서 몸체와 그 체형용 의상은 같은 기준 포즈와 호환되는 본 계층을 사용한다.
2. 다른 BodyProfile은 다른 스켈레톤 에셋을 사용할 수 있다. 플러그인 전역에 하나의 스켈레톤을 강제하지 않는다.
3. 최초 포즈 전달은 Leader Pose 기반이다. 의상에 독자적인 추가 본 애니메이션이나 천 물리를 요구하지 않는다. 독자 포즈가 필요한 옷은 향후 별도 결합 방식을 추가한다.
4. 같은 GarmentPreset의 체형별 GarmentFit은 같은 PatternSchema를 구현한다. 메시 정점 수·스키닝은 달라도 그림의 부위와 UV 의미는 같아야 한다.
5. 그림을 다른 체형에 옮길 때는 RGB 데이터를 그대로 쓰고 대상 GarmentFit만 바꾼다. 임의의 다른 옷본에 자동 변환하지 않는다. 비율 차이에 따른 그림의 물리적 늘어남은 해당 체형용 UV 검수로 관리한다.

UE의 Leader Pose는 자식의 일치하는 본 구조와 기준 구성을 요구하며, 독립 포즈·물리에 제약이 있다. 컴포넌트 수에 따른 렌더링 비용도 남는다. 이 제약 때문에 체형별 맞춤과 애니메이션 검증을 에셋 계약에 포함한다. [Epic UE 5.7 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine?application_version=5.7)

### 관통과 조합 호환성

BodyProfile은 몸통·골반·좌우 위팔·아래팔·허벅지·종아리 등의 영역 ID를 정의한다. 최초 몸체는 영역별로 숨길 수 있는 메시 섹션과 모든 LOD의 대응표를 제공한다. 장착한 GarmentFit의 가림 영역 합집합으로 몸체 섹션의 표시를 갱신한다. 몸체 전체나 본을 통째로 제거해 애니메이션을 깨뜨리지 않는다.

몸체 가림은 옷끼리의 관통까지 해결하지 않는다. 최초 3개 상의와 3개 하의는 같은 체형에서 모든 9개 조합을 검수하는 것을 콘텐츠 계약으로 삼는다. 허리 경계·소매·후드와 기본 머리의 간섭도 확인한다. 후속 콘텐츠는 BodyProfile별 조합 허용표를 명시하고, 등록되지 않은 조합은 장착을 거절한다.

체형 전환은 현재 장착 의상 전체의 대상 GarmentFit과 조합 호환성을 먼저 확인한다. 하나라도 없으면 전체 전환을 거절하고 기존 캐릭터를 유지한다. 부분적으로 옷이 사라지는 전환은 하지 않는다.

범용성 검증용으로 별도 스켈레톤 에셋과 약 4.5등신 비율을 가진 두 번째 테스트 BodyProfile을 준비한다. 티셔츠·긴바지·원피스의 3개 대응 GarmentFit만 만들고 동일 디자인을 적용해 확인한다. 이는 8종 기본 옷본을 늘리는 별도 제품 체형 팩이 아니라 검증용 에셋이다.

## 6. 최초 옷본과 그림 부위

| 분류 | 옷본 | 대표 편집 부위 |
|---|---|---|
| 상의 | 반팔 티셔츠 | 몸통 앞·뒤, 왼쪽·오른쪽 소매 |
| 상의 | 긴팔 셔츠 | 몸통 앞·뒤, 왼쪽·오른쪽 소매, 깃 |
| 상의 | 후드 상의 | 몸통 앞·뒤, 왼쪽·오른쪽 소매, 후드 바깥·안쪽 |
| 하의 | 긴바지 | 왼다리 앞·뒤, 오른다리 앞·뒤 |
| 하의 | 반바지 | 왼다리 앞·뒤, 오른다리 앞·뒤 |
| 하의 | 치마 | 앞·뒤·왼옆·오른옆 |
| 한 벌 | 원피스 | 상체 앞·뒤, 좌우 소매, 치맛단 앞·뒤·좌우 |
| 한 벌 | 점프수트 | 상체 앞·뒤, 좌우 소매, 왼다리 앞·뒤, 오른다리 앞·뒤 |

부위는 “몸체 슬롯”이나 별도 텍스처가 아니라 단일 이미지 안의 편집 영역이다. 부위 선택은 같은 64×64 캔버스의 영역을 강조·확대하고 붓 입력을 제한하는 기능이다. 한 벌 의상도 하나의 디자인 파일과 하나의 장착 항목이며, 편집 영역이 여러 개라는 이유로 상하 분리 장착을 허용하지 않는다.

최초 PatternSchema는 옷 전체 64×64 픽셀을 사용하는 고정 배치이며 최대 16개의 이름 붙은 편집 영역을 허용한다. 영역 수를 늘려도 총 픽셀 수 4,096은 증가하지 않는다. 몸통·소매·다리 등 영역의 크기와 모양은 옷본마다 다르게 배분한다. 큰 앞뒤 면에 우선 면적을 주고 깃·후드 안쪽 등의 작은 면에는 적게 배분한다. 각 영역에 32×32 같은 최소 크기를 일괄 보장하지 않는다. 옷본의 모든 보이는 면은 이 한 장에서 색을 얻도록 UV를 준비한다.

스키마는 전체 픽셀을 쓰기 가능한 영역, 필요할 때 경계색을 복제하는 보호 영역, 미사용 영역으로 구분한다. 쓰기 가능 픽셀은 정확히 한 편집 영역에 속한다. 보호 영역은 스키마에 지정된 쓰기 가능 원본 픽셀을 참조하고, 미사용 영역은 스키마 기본색으로 정규화한다. 보호 여백도 64×64 안에 포함하며 별도 외곽 아틀라스나 큰 텍스처로 확장하지 않는다. 좌우 비대칭 그림을 지원하므로 독립적으로 편집할 좌우 면의 UV를 겹치지 않게 한다.

그림 저장 원본과 표시용 텍스처 크기는 모두 64×64다. 렌더링 시에는 RGB에 alpha 255를 붙인 RGBA8 텍스처 하나를 사용하며, 의상 메시가 여러 섹션을 쓰더라도 같은 사용자 디자인 텍스처를 참조한다. 옷본의 공통 음영·재질 표현은 별도로 유지할 수 있다. 부위별 텍스처 객체·렌더 타깃·별도 픽셀 저장 배열을 만들지 않는다.

최초 표시는 최근접 샘플링, mip 비활성화, U/V Clamp를 기준으로 검수한다. 원거리 작은 무늬의 깜빡임은 별도로 관찰하며, 필요하면 영역 경계를 보존하는 mip 생성 규칙을 검증한다. 자동 mip 생성이나 선형 필터만 켜서 맞닿은 다른 부위의 색이 섞이게 하지 않는다. 필터·주소 모드·mip 설정의 엔진 동작은 [Epic UE 5.7 텍스처 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-asset-editor-in-unreal-engine?application_version=5.7)를 따른다.

### 옷본과 반복 무늬의 호환 조건

단일 텍스처 사용은 옷본 프리셋 구조와 양립한다. GarmentPreset마다 고정 PatternSchema를 두고 각 체형용 GarmentFit이 같은 UV 의미를 구현하면 된다. 상의·하의·한 벌에 동일한 영역 배치를 강제하지 않으며, 모든 옷을 하나의 공용 그림으로 묶지도 않는다. 서로 다른 옷본 사이에 완성 그림을 임의로 옮기는 것은 최초 범위가 아니다.

체크·줄무늬 등 반복 무늬는 옆구리·어깨·소매·다리의 연결부에서 방향과 간격이 어긋날 수 있다. 스키마는 주요 연결 경계의 대응 방향과 영역 안의 기준점을 기록하고, 모델 제작 시 같은 원단처럼 이어질 면의 픽셀 밀도를 가능한 한 맞춘다. 테스트용 체크·줄무늬로 주요 이음새를 검수한다. 임의 그림의 이음새를 자동 수정하거나 모든 체형에서 물리적인 무늬 크기까지 같게 만드는 기능은 포함하지 않는다.

반복 무늬가 필요하더라도 완성 아틀라스 전체를 UV Wrap으로 반복하면 다른 부위의 그림까지 반복된다. 최초에는 한 장에 그려진 그림을 그대로 사용한다. 향후 무늬 채우기 도구를 추가할 때는 각 영역의 원단 좌표와 시작 위치를 맞춰 결과를 이 한 장에 굽는 방식으로 확장한다. 이는 별도 부위 텍스처를 추가하라는 뜻이 아니다.

한 벌·후드처럼 면이 많은 옷은 같은 4,096픽셀을 더 나눠 쓰므로 작은 글자나 세밀한 그림 표현이 줄어든다. 이 한도는 64×64 규격을 유지하는 설계상의 제약이다. 첫 옷본의 UV와 체크·줄무늬·대표 그림 미리보기를 검수한 뒤 나머지 옷본을 제작하며, 보기 좋게 만들기 위해 옷마다 해상도를 임의로 높이지 않는다.

UV 배치를 변경할 때는 PatternSchema 버전을 갱신한다. 실행 중 자동 재배치나 기존 이미지의 조용한 재해석은 하지 않는다. 다른 해상도는 사용자가 나중에 규격 변경을 요청할 때 별도로 설계한다.

## 7. 장착 규칙

저장되는 정상 상태는 다음 두 형태 중 하나다.

- Separate: Top과 Bottom에 각각 0개 또는 1개. FullBody 참조는 없음.
- FullBody: 한 벌 참조 1개. Top과 Bottom 참조는 없음.

빈 슬롯에서는 BodyProfile의 기본 내의 외형이 보인다. 숨겨진 “이전에 입은 상하의” 상태를 따로 유지하지 않는다.

| 기존 상태 | 명령 | 성공 후 상태 |
|---|---|---|
| Separate | 상의 장착 | 상의 교체, 기존 하의 유지 |
| Separate | 하의 장착 | 하의 교체, 기존 상의 유지 |
| Separate | 한 벌 장착 | 상의·하의 참조 제거, 한 벌 장착 |
| FullBody | 상의 장착 | 한 벌 제거, 상의 장착, 하의는 빈 슬롯 |
| FullBody | 하의 장착 | 한 벌 제거, 하의 장착, 상의는 빈 슬롯 |
| FullBody | 한 벌 장착 | 기존 한 벌을 새 한 벌로 교체 |
| Separate | 한 슬롯 해제 | 해당 슬롯만 비움 |
| FullBody | 상의 또는 하의 위치에서 해제 | 한 벌 전체를 해제하고 두 슬롯을 비움 |

원피스를 상의만 남기는 식으로 부분 해제하지 않는다. 서로 충돌하는 조합으로 상의 또는 하의를 교체하려고 하면 상대 슬롯을 임의로 비우지 않고 요청 전체를 거절한다.

장착·해제·체형 변경은 하나의 완성된 다음 AppearanceSnapshot을 만든 뒤 처리한다. ID, 스키마, GarmentFit, 조합, 에셋 로드와 머티리얼 준비를 모두 확인한 후 한 번에 교체한다. 준비 또는 저장 실패 시 이전 상태와 화면을 유지한다. 비동기 로드 중 뒤늦게 끝난 과거 요청은 요청 번호로 폐기한다.

## 8. 텍스처 편집 기능

첫 편집기는 아래 기능을 제공한다.

- 옷본과 편집 부위 선택, 단일 64×64 전체 캔버스 보기, 선택 영역 확대·축소, 유효 영역과 부위 이름 표시.
- 연필 1·2·4픽셀, 기본 그림으로 되돌리는 지우개, 스포이트, 전체 부위 채우기.
- 같은 RGB 값으로 연결된 4방향 영역 채우기. 단일 이미지에서 서로 맞닿아 있어도 다른 부위나 보호·미사용 영역으로 번지지 않는다. 전체 보기에서도 그림을 시작한 영역의 경계를 따른다.
- RGB 색 선택과 팔레트, 현재 부위의 좌우 대칭 그리기.
- 같은 크기 부위의 복사·붙여넣기와 좌우 대응 부위 복사. 좌우 방향 변환은 스키마를 따르고 같은 이미지 안의 대상 유효 영역만 변경한다. 크기가 다른 영역은 자동 리사이즈하지 않고 거절한다. 대칭 편집은 선택 부위의 로컬 축을 기준으로 하며 전체 UV 배치를 뒤집지 않는다.
- 실행 취소·다시 실행. 한 번의 드래그·채우기·복사를 각각 한 작업으로 취급하며 전체 편집 세션에서 최대 100작업 또는 16MiB 중 먼저 도달한 한도를 사용한다.
- 캐릭터 회전·확대·축소, 정면·후면 확인, 정지·걷기·팔 올리기·앉기의 검사용 포즈. BodyProfile은 이 네 포즈를 제공한다.
- 디자인 신규 생성·이름 변경·복제·저장, 저장된 디자인 선택·착용·삭제.

RGB는 불투명 색이다. 최초 지우개는 투명 구멍을 만들지 않는다. 노멀·러프니스·천 재질의 기본 표현은 옷본의 머티리얼이 담당하며, 사용자는 색과 그림을 편집한다. 여러 레이어, 외부 이미지 불러오기, PNG 내보내기, 브라우저 공유·마켓은 후속 기능이다.

EditSession의 단일 64×64 RGB 버퍼가 작업 원본이다. 표시용 텍스처는 여기서 생성하며, Render Target을 읽어 저장 원본으로 삼지 않는다. 드래그 중 바뀐 사각 영역과 연결된 보호 픽셀만 같은 텍스처에 반영하고 텍스처 객체를 픽셀마다 새로 만들지 않는다. 부위별 확대 화면도 동일 버퍼의 좌표를 읽는다. 실제 업로드 API와 스레드 처리는 UE 5.7에서 확인해 선택한다.

## 9. 편집·저장·착용의 구분

편집을 열 때 저장된 DesignRevision을 복사해 초안을 만든다. 새 디자인은 옷본의 기본 그림으로 시작한다. 편집 중 미리보기는 EditSession의 전용 대상에만 반영한다. 다른 캐릭터가 같은 디자인을 착용하고 있어도 영향을 받지 않는다.

- 저장: 검증된 새 DesignRevision을 라이브러리에 추가한다. 편집 화면의 저장 기준점을 갱신한다. 장착 상태는 별도다.
- 착용: 이미 저장된 정확한 DesignRevision을 선택한 CharacterId에 적용하고 AppearanceSnapshot을 기록한다.
- 취소·닫기: 마지막 저장 이후의 초안을 버린다. 이미 저장된 버전을 삭제하지 않는다. 장착된 캐릭터의 외형을 변경하지 않는다.
- 삭제: DesignId 전체를 대상으로 한다. 어느 버전이든 참조하는 로컬 캐릭터 기록이나 열린 편집 세션이 있으면 해제·닫기 전까지 거절한다. 허용되면 해당 디자인의 모든 버전과 색인 항목을 삭제한다.

최초 라이브러리 UI는 DesignId별로 한 항목을 표시하고 최신 저장 버전만 편집·새로 착용한다. 이전 버전 탐색·개별 버전 삭제·과거 버전으로 되돌리기는 제공하지 않는다. 이전 버전은 이미 착용한 외형의 복원을 위해 내부에 유지하며 자동 정리하지 않는다. 착용한 과거 버전으로부터 직접 편집을 여는 별도 진입점도 최초 범위에 포함하지 않는다.

저장과 착용을 분리하는 것은 이번 설계의 제안이다. UI에서 미저장 초안을 직접 착용시키지 않는다. 추후 “저장 후 착용” 동작을 추가하더라도 새 버전 저장 성공 후 장착을 수행하고, 장착 실패를 디자인 저장 성공과 구분해 보고해야 한다.

## 10. 영속 데이터 계약

저장 제공자는 호스트가 루트 경로와 사용자·빌드 네임스페이스를 주입한다. 독립 예제의 기본 루트는 프로젝트 Saved/GarmentDesigner/Local이다. 기존 게임과 연동할 때는 게임 쪽 어댑터가 현재 계정·배포판 격리 정책을 적용한다. 플러그인은 Steam, 게임 진행 슬롯, 현재 플레이어 GameInstance에 의존하지 않는다.

| 파일 | 내용과 규칙 |
|---|---|
| Designs/DesignId/Revision.gdesign | 스키마 버전·메타데이터·단일 64×64 RGB 이미지·내용 해시를 담는 불변 기록 |
| Characters/CharacterId.json | 몸체 프로필과 Separate/FullBody 상태, 정확한 디자인 버전 참조, 외형 Revision |
| LibraryIndex.json | 디자인 목록과 사용자 표시 이름을 빠르게 찾는 재생성 가능한 색인 |

DesignId와 CharacterId는 GUID, Revision은 양의 정수다. GUID와 Revision으로만 파일명을 생성한다. 표시 이름을 경로에 넣지 않는다. 메타데이터는 최대 16KiB, 논리 편집 영역 수는 최대 16이다. 픽셀 원본은 항상 64×64 RGB8로 정확히 12,288바이트이며, 좌상단부터 행 우선으로 R/G/B를 저장한다. 보호·미사용 영역도 이 이미지 안에 포함한다. 디자인 기록 전체의 최대 허용 크기는 64KiB이며 읽기 전에 길이·버전·해시·ID·스키마를 검증한다.

파일 envelope의 구체적인 직렬화 구현은 구현자가 선택하되 magic, 포맷 버전, 메타데이터 길이, 픽셀 길이, 정규화된 내용의 SHA-256 검증을 포함한다. 해시는 포맷 버전·PresetId·SchemaId·스키마 버전·폭 64·높이 64·정규화된 단일 RGB 이미지 바이트를 대상으로 하며, 화면용 표시 이름과 로컬 파일 경로는 포함하지 않는다. 저장 전 보호 영역을 지정된 원본 색으로 갱신하고 미사용 영역을 기본색으로 정규화하며, 읽을 때도 이 조건을 검증한다. 라이브러리 이름 변경은 새 픽셀 버전을 만들지 않으며 색인에 저장한다. 색인이 없으면 원본 기록의 생성 당시 이름으로 복구할 수 있다.

동일 저장 네임스페이스에는 쓰기 가능한 프로세스를 하나만 허용한다. 저장 제공자를 열 때 프로세스 수명의 배타 잠금을 획득하며, 두 번째 프로세스는 읽기 전용으로 열고 저장·이름 변경·착용 기록 변경·삭제를 거절한다. 잠금은 프로세스 종료 시 해제되는 OS 자원으로 보장하며, PID를 적은 파일의 존재 여부만으로 판정하지 않는다. 구현 플랫폼에 따른 잠금 API는 저장 제공자 내부에서 선택한다.

하나의 쓰기 프로세스에서도 네임스페이스별 변경 큐로 디자인 저장·색인 갱신·착용·체형 변경·삭제를 직렬화한다. 삭제의 전체 참조 검사와 실제 삭제는 같은 작업 범위 안에서 처리한다. EditSession은 시작 시 최신 DesignRevision을 기억하고, 저장 시 실제 최신 버전과 다르면 RevisionConflict를 반환해 초안을 보존한다. 새 Revision 할당과 기존 파일을 덮어쓰지 않는 게시도 같은 변경 큐 안에서 수행한다.

디자인 저장은 새 불변 파일을 임시 파일에 쓰고 검증한 뒤 최종 이름으로 원자적으로 게시한다. 색인 갱신이 실패하면 원본 파일을 지우지 않고 다음 목록 읽기에서 재색인한다. 착용 기록은 새 파일을 검증한 뒤 기존 파일을 원자적으로 교체하며, 교체 전에 기존 파일을 삭제하지 않는다. 외형 기록에는 예상 Revision을 비교해 다른 창의 변경을 덮어쓰지 않는다.

외형 변경 처리 순서는 준비된 다음 상태 생성 → 모든 표시 자원 준비 → CharacterId 기록 교체 → 게임 스레드에서 표시 자원 일괄 교체 → 변경 알림이다. 준비된 자원의 활성화 단계에는 추가 로드나 파일 쓰기를 넣지 않는다. 외형 기록 쓰기 실패 시 준비 자원을 해제하고 원래 화면과 상태를 보존한다. 프로세스가 기록 교체 후 종료되면 다음 실행에서 저장된 다음 상태를 복구한다.

변경 큐가 외형 작업을 시작하기 직전에 최신 요청 번호·예상 외형 Revision·대상 유효성을 다시 확인한다. 여기서 폐기된 요청은 디스크에 쓰지 않는다. 기록 교체가 시작된 작업은 표시 교체·알림까지 하나의 완료 단위로 끝내고, 그동안 들어온 새 요청은 다음 순서로 처리한다. 대상 Actor가 그 사이 파괴되면 저장 결과는 유지하고 표시 단계만 생략한다. 다음 로드에서 저장 상태를 복원한다. 늦게 도착한 로드 결과나 요청 취소가 디스크와 화면을 서로 다른 Revision으로 남기지 않게 한다.

삭제 중 종료되어 일부 버전만 제거되는 문제를 막기 위해, 참조 검사 후 DesignId 디렉터리를 같은 볼륨의 삭제 대기 위치로 원자적으로 이동해 먼저 라이브러리에서 제외한다. 이동 전까지는 전체가 존재하고 이동 후에는 전체가 삭제된 상태다. 대기 위치는 다음 실행에서 정리할 수 있으며 재색인·복구 원본에 포함하지 않는다. 이 절차 역시 네임스페이스 변경 큐에서 처리한다.

초안, 실행 취소 기록, 선택 부위·색, 카메라, 생성된 텍스처와 미리보기 Actor는 저장하지 않는다. 임시 파일은 복구 원본이나 동기화 대상이 아니다. 알 수 없는 버전·없어진 옷본·호환되지 않는 체형은 원본 기록을 유지하고 현지화된 오류를 반환한다. 시작 시 표시를 복구할 수 없으면 기본 외형을 임시 표시하며 이를 정상 장착 상태로 저장하지 않는다.

실제 구현에서 이 계약에 해당하는 데이터를 추가할 때 [저장 현황](../../save_persistence.md)에 별도 항목을 추가한다. 이번 설계만으로 현재 저장 버전과 런타임 데이터를 변경하지 않는다. Cloud 등록·자동 동기화는 포함하지 않는다.

## 11. 외형 전달과 호스트 접점

코어의 공개 계약은 BodyProfile 초기화, 디자인 목록·편집 세션, 저장, 장착·해제, 체형 변경, AppearanceSnapshot 내보내기·적용, 성공·실패 결과와 변경 알림이다. UI는 이 계약을 호출한다. 월드 액터 탐색이나 현재 플레이어 검색으로 대상을 추론하지 않고 대상 컴포넌트와 CharacterId를 전달받는다.

동일 외형을 다른 실행 환경에서 보여줄 수 있도록 다음 데이터 계약을 확보한다.

- 외형 스냅샷에는 상태 Revision과 정확한 디자인 버전·내용 해시가 들어간다.
- 원격 전달 묶음에는 CatalogId와 CatalogCompatibilityVersion도 포함한다. 최초 전송 계약은 두 값이 일치하는 콘텐츠 카탈로그끼리만 허용한다. 같은 에셋 ID에 다른 기준 포즈·메시·UV·머티리얼이 연결되는 변경은 이 호환 버전을 갱신한다. 에디터 검증기는 배포용 카탈로그에 기록한 에셋 의존 지문과 현재 에셋을 대조해 버전 갱신 없는 변경을 검출한다.
- 수신자는 필요한 디자인 기록을 캐시에서 찾거나 호스트가 주는 바이트로 받아 검증한다. 메시·스켈레톤·머티리얼 에셋을 디자인 파일 안에 넣어 전송하지 않는다.
- 대상이 모르는 PresetId·SchemaId·체형은 적용하지 않는다. 모든 데이터가 준비되기 전에는 이전 완성 외형 또는 기본 외형을 유지한다.
- 오래된 외형 Revision이 최신 상태를 되돌리지 않도록 한다. 그림을 한 픽셀 칠할 때마다 원격으로 보내는 계약은 두지 않는다.

픽셀 내용 해시는 메시와 머티리얼의 동일성을 보장하지 않는다. 서로 다른 카탈로그 버전 간의 원격 변환은 최초 범위가 아니다. 로컬에서 새 체형을 등록해 기존 그림을 사용하는 규칙은 5절의 PresetId·PatternSchema 계약으로 판단하며, 네트워크 카탈로그 버전 변경만으로 로컬 RGB 기록을 다시 작성하지 않는다.

최초 로컬 기능에는 실제 세션·서버·RPC·Steam/EOS 연동을 포함하지 않는다. 협동 플레이에 연결하는 단계에서 호스트가 권한 검사, 연결별 전송량 제한, 청크 전송·재시도·접속 중인 대상의 전체 스냅샷 전달을 담당한다. 원격 적용은 로컬 캐릭터 저장을 자동 변경하지 않는 별도 경로다. 이 설계의 완료를 멀티플레이 구현이나 동기화 검증 완료로 해석하지 않는다.

## 12. 플러그인 구조와 UI 규칙

| 모듈 또는 콘텐츠 | 역할 |
|---|---|
| GarmentDesigner, Runtime | 데이터, 편집 버퍼, 저장 계약, 외형 조립·검증. UMG 의존 없음 |
| GarmentDesignerUI, Runtime | 편집기·라이브러리와 미리보기 제어. Core 모듈과 UMG 의존 |
| GarmentDesignerEditor, Editor | 체형·의상·스키마·UV·LOD·조합 등록 검증. 패키지 런타임에서 제외 |
| 플러그인 Content | 체형·옷본·머티리얼·WBP·문자열 테이블·독립 예제 맵. 프로젝트의 /Game 에셋에 필수 의존하지 않음 |

플러그인의 코드·콘텐츠와 Runtime/Editor 분리는 UE 플러그인 구조를 따른다. Content 사용을 선언하고, 독립 예제에서 필요한 에셋을 명시적으로 참조해 패키징 시 포함되게 한다. [Epic UE 5.7 플러그인 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine?application_version=5.7)

플러그인은 TunaSweeper, MiyakovCharacterSystem, 기존 아이콘 위젯과 플레이어 클래스에 대한 빌드·콘텐츠 의존성을 두지 않는다. 최초 구현의 프로젝트 현지화 어댑터는 게임 모듈 쪽에서 플러그인을 참조하고 문자열 제공자만 연결한다. 예제 맵은 플러그인 자체의 기본 몸체와 옷을 사용한다. 현재 프로젝트의 기본 맵·GameMode·플레이어 HUD를 변경하지 않는다.

UI의 모든 라벨·오류·도구 이름은 ui.garment_designer.* 문자열 키로 해석한다. 플러그인에는 독립 실행용 문자열 테이블 제공자를 두고, 현재 프로젝트의 어댑터는 기존 UITextStrings.csv와 현지화 흐름으로 해석한다. 최초 구현에서 두 테이블에 필요한 키를 추가하고 키·번역 일치 여부를 검증한다. 호스트 제공자가 등록된 경우 그 제공자를 사용하며, 빈 검증 프로젝트에서는 플러그인 테이블을 사용한다. 어댑터는 언어 변경 알림도 전달한다. 구현에 하드코딩한 표시 문자열을 fallback으로 넣지 않는다. 사용자 입력 디자인 이름은 시스템 UI 문구와 구분한다. ko, en, ja, zh-Hans, zh-Hant, ru를 검증한다.

프로젝트의 위젯 규칙을 그대로 적용한다.

- 위젯 소스는 실제 구현 모델 이름의 중간 디렉터리에 둔다.
- 클래스 이름은 실제 기능과 확인된 모델 이름만 포함한다. 프로젝트명이나 추론 강도를 넣지 않는다.
- 소스에 실제 모델명과 추론 강도를 기록한다. 이번 설계에서 구현 모델·강도를 추측하거나 미리 배정하지 않는다.
- 파생 Widget Blueprint 이름에는 확인된 모델 접미사를 붙인다.
- 위젯 트리는 실제 WBP 에셋에 저장한다. 위젯 클래스에서 ConstructWidget, AddChild 등으로 트리를 생성하지 않는다. 픽셀 캔버스의 직접 그리기는 트리 생성과 구분한다.
- 일회성 에셋 생성기가 필요하면 에셋 검증 후 생성기·진입점·전용 의존성을 제거하고 재검증한다. 시작할 때 UI를 재생성하는 경로를 남기지 않는다.

구체적인 화면 배치·색상·아이콘과 미리보기 배경은 기능 계약을 유지하는 범위에서 UI 제작자가 정한다. 이 문서는 UI 시안이나 편집 가능한 WBP를 이미 제작했다는 의미가 아니다.

## 13. 오류와 자원 수명

오류 결과는 MissingPreset, UnsupportedSchema, MissingFit, IncompatibleCombination, InvalidDesign, SaveFailed, RevisionConflict 등 값 코드와 문자열 키를 반환한다. 프레임별 경고 팝업을 띄우지 않고 해당 작업 결과에 표시한다.

미리보기는 캐릭터와 몸체 프로필·초안을 소유한 세션의 수명에 묶는다. 닫기·월드 종료·대상 파괴 시 입력 캡처, 비동기 콜백, 텍스처·메시 참조를 해제한다. 완료된 과거 요청의 콜백으로 이미 닫힌 세션을 복구하지 않는다. 코어가 게임 전체를 일시정지하거나 입력 모드를 바꾸지 않으며, 필요한 호스트 UI가 진입 시 상태를 저장하고 종료 시 복원한다.

동일 내용 해시의 확정 텍스처는 캐시로 공유할 수 있으나 각 세션의 초안 텍스처는 공유하지 않는다. 옷 하나의 RGB 원본은 12KiB이고, 64×64 RGBA 표시 텍스처는 mip·GPU 정렬·객체 오버헤드 제외 16KiB다. 상하 분리 장착은 사용자 디자인 텍스처 두 장, 한 벌은 한 장을 사용한다. 캐릭터 수가 늘 때 그리기 호출 수와 캐시 메모리를 실제로 측정하고, 측정 없이 임의의 동시 캐릭터 성능을 보장하지 않는다.

이 검증표는 앞으로 구현할 기능의 수용 기준이다. 이번 문서 작성으로 테스트가 통과한 것은 아니다. 실제 저장 테스트는 격리된 임시 네임스페이스를 사용한다.

## 15. 구현자에게 남기는 선택과 검토 항목

알고리즘의 내부 자료구조, 구체적인 C++ 함수명, 검증 도구의 에디터 UI, 파일 envelope 직렬화 라이브러리, UI 배치는 위 계약을 지키는 범위에서 구현자가 정한다. 사용자 확정 요구를 바꾸거나 임의 자동 피팅·플레이어 통합·체형 편집기를 추가하는 것은 여기에 포함하지 않는다.

옷 전체 64×64 단일 텍스처는 사용자 확정 규격이다. 구현 전 사용자 검토에서 특히 확인할 나머지 제안은 초기 8종 옷본, 약 3등신 최초 체형, 체형별 맞춤 메시 등록 방식, 저장과 착용의 분리, 최초 로컬 구현 범위다. 설계 검토 이후 구현 계획을 별도로 작성한다. 명시적인 커밋 요청이 없는 현재 작업에서는 커밋하지 않는다.
